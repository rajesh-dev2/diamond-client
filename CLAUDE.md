## Business context
- "Diamond" is a betting-exchange platform. The business/domain was rebranded to **primeexch99.co** (MongoDB `domain` field on `sports` was migrated from `"diamond"` to `"primeexch99"`).
- It runs on the **same vendor software family** ("icebook") as several other exchange panels: riceexch.com, allpanelexch9.game, diamondexch99.now — same AES encryption scheme, same `/api/admin/treedata2..5`, `/api/admin/game/gameDataPrivate`, `/api/admin/game/gameDetailPrivate` endpoint contract.
- **sky99** is a separate, older, already-working exchange product (its own `feed-server` scrapes `allpanelHub`-style sources and exposes `api.sky99.co/api/public/*`). Diamond used to depend on sky99's API directly; the whole point of this project was to make diamond **fully independent** of sky99, with its **own** scraper hitting riceexch/allpanelexch9/diamondexch99 directly, replicating **sky99's own architecture** where sky99 already solved the same problems well. That decoupling is done — diamond no longer calls sky99 for anything.

## What has been built
1. **`/root/riceexch-scraper/server.js`** on the scraping server (192.241.135.125) — a drop-in replacement for `api.sky99.co/api/public/*`, so diamond-api's existing sync jobs work unmodified against it. Key pieces:
   - `SOURCES[]`: riceexch.com / allpanelexch9.game / diamondexch99.now, each with its own Chrome+CDP session, proxy, login creds, and independent priority queue.
   - **Cascading fallback** (`withSourceFallback`): tries each source in order; whichever succeeds first is cached per-gmid in `_gmidSourceMap` so repeat lookups skip the fallback.
   - **Priority queue per source** (`initQueue`/`processQueue`/`withSlot`): two lanes, `high` (live odds) and `low` (background match-listing cascade: treedata2→3→4). `MAX_CONCURRENT_HIGH=2` batches up to 2 high-priority calls together (mirrors sky99's `FAST_BATCH_SIZE=2` in `allpanelHub.ts`). `HIGH_STREAK_LIMIT=10` forces an occasional low-priority slot so the background cascade isn't starved.
   - **`oddsFastLoop()`** — a single shared tick-based loop (mirrors sky99's `fastLoop()`), self-correcting cadence (~500ms), that fires **all currently-active gmids together in one synchronous pass** every tick. This replaced an earlier per-gmid-independent-while-loop design that had a microtask-ordering race preventing true batching. Fixed by (a) deferring `processQueue()`'s trigger to a microtask in `withSlot()`, and (b) driving all active gmids from one shared loop instead of N independent loops.
   - Endpoint parity with sky99: `GET /api/public/sports|series|events|events/:cid|all-events|all-series|match/:gmid(/raw)|treedata1..5|health`.
   - **`cricket-score-service`** (separate, port 4010 on the main server) ports sky99's own `cricketScoreService.ts` using the public goscorer/crickapi source, wired into this repo's `src/components/game-details/Scorecard` component (`useGetScorecardQuery` in `src/store/api/authApi.js`, `transformScorecard()` in `src/components/game-details/utils.js`; mock/demo data removed per explicit instruction).
2. **diamond-api `.env`** repointed (`SPORTS_API_URL`, `SERIES_API_URL`, `EVENTS_API_URL`, `MATCH_API_URL`, `TREE_API_URL`) from `api.sky99.co` to `http://192.241.135.125:4001/api/public/...`.

## Current state (as of 2026-09-15)
- All 3 sources report healthy. Background match-listing cascade works (cricket: ~23 series, football: 121 matches discovered).
- Live-odds latency was the main open problem across many iterations. Root causes found and fixed, in order:
  1. `_gmidSourceMap` wasn't being populated on the "cold" fallback path → every poll re-did the expensive 3-source fallback. Fixed.
  2. Background low-priority cascade calls (`treedata3` etc.) were interrupting the live-odds queue too often at `HIGH_STREAK_LIMIT=5`, causing multi-second catch-up spikes. Raising the limit to 200 removed the spikes but revealed a second, deeper bug.
  3. **The real bug**: independent per-gmid polling loops had a microtask race that prevented true 2-way batching — `queueWait` was stuck at ~2000ms per gmid instead of ~450-700ms. Fixed via the shared `oddsFastLoop()` + deferred `processQueue()` trigger described above.
  4. Side-effect: with the high lane almost never idle, the background cascade briefly starved completely. Fixed by lowering `HIGH_STREAK_LIMIT` to 10 (forces a low-priority turn roughly every 5-8 seconds — an acceptable, bounded ~650-900ms blip rather than indefinite starvation).
  - **Verified result**: `queueWait` steady at ~450-700ms per gmid (matches sky99's own ~500-900ms cadence), with an occasional (~1-in-8) brief ~2s blip when the background cascade takes its turn — self-recovering, not compounding.
- **Separately discovered, not a bug in this code**: diamond-api's own compiled `liveMarketSyncJob` was continuously logging `Match provider is currently unavailable` and retrying for the test match used during development (gmid 878759716, England U19 v Pakistan U19) — because that match's upstream data genuinely has no "Match Odds" market (only Bookmaker/Fancy/Meter/Oddeven/CricketCasino). ~30 other currently-listed cricket/football matches were checked — none had an active Match Odds market either at the time (most hadn't started). This is a data-availability characteristic of the source panel, not fixable by tuning the scraper.
- **That test match has since ended** (`isLive:false` in MongoDB `events`), as has the other test match (a virtual/simulated fixture with zero real markets). Both currently-"active" DB entries are effectively dead. **A fresh live match needs to be activated** (in diamond-admin, or via a direct Mongo `events.updateOne({gmid}, {$set:{isActive:true}})`) to continue verifying the live-odds pipeline end to end — ideally one with a real Match Odds market.

## Constraints to respect (learned the hard way)
- **Never be aggressive against riceexch/allpanelexch9/diamondexch99** — Cloudflare WAF blocks trigger easily on rapid automated requests. If a source shows a CF challenge/WAF block, do not attempt scripted mouse/scroll evasion — ask the operator to clear it manually via VNC, or fail over to another proxy IP/source.
- Every request to `/api/public/match/:gmid` registers that gmid into the shared odds-polling set for 60s (`ODDS_IDLE_STOP_MS`) — **don't bulk-scan many gmids this way** just to "check market composition"; it dilutes `MAX_CONCURRENT_HIGH` batching for whatever is genuinely live and reintroduces the latency problem described above. Use the raw `treedata4/5` passthrough or a narrow, deliberate check instead.
- Keep the **2-matches-per-source** active limit (load management) unless told otherwise.
- `diamond-api`'s own code is compiled/protected — cannot be edited. Any new feature (e.g., cricket scorecards) must be added via a new standalone service + a more-specific nginx route, never by touching `diamond-api` directly.
- Deploy pattern for `server.js` on the scraping server: edit locally → `node --check` → `scp` to `/root/riceexch-scraper/server.js` → `node --check` again remotely → `pm2 restart riceexch-diamond-api`. Never skip the syntax check.
- Diagnose latency claims with real measurements (the `[timing] {label} queueWait=Xms exec=Yms` logs and the `ageMs` field on `/api/public/match/:gmid` responses), not assumptions.

## What "done" looks like, sky99-style
sky99's `allpanelHub.ts` achieves accurate near-instant odds despite only ~1s-ish polling because of **one shared loop batching all currently-live slots together every tick**, not raw per-call speed. Diamond's scraper now mirrors that exact shape (`oddsFastLoop`). The remaining work here is operational, not architectural: keep 1-2 genuinely live matches active (ideally with a real Match Odds market) and confirm `ageMs`/`queueWait` stay in the ~450-900ms band sky99 itself operates in.
